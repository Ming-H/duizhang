# 对账 v0.4 设计：单机生产级容量（8GB / 47GB 磁盘约束下）【历史存档】

> **时效说明**：容量推导与备选取舍仍然有效。Phase 1 中「分年分库」与
> 「摄取并行化」在当前语料规模（~1,100 份）下属非目标，见 DESIGN-v0.4.md §2；
> FTS5 检索层已于 v0.4 落地验收。

> 结论先行：8GB 内存不是容量障碍，**全内存索引才是**。检索层换 SQLite FTS5
> 磁盘倒排后，容量瓶颈从内存转移到磁盘——本机 47GB 可用磁盘装得下
> 全 A 股 5 年的文本层（约 3,000 万 chunk），内存常驻降到 ~2GB。

## 1. 现状实测（v0.3，本机）

| 指标 | 实测值 | 换算 |
|---|---|---|
| 语料 | 1,103 文档 / 60.7 万 chunk | 551 块/文档（含 232 页年报，偏高） |
| 内存（全量驻留） | 1.8 GB | **3 KB/chunk** ← 天花板的根源 |
| sqlite | 210 MB（text 本体 ~170MB） | ~280 B/chunk 文本 |
| 索引 pickle | 497 MB | ~0.8 KB/chunk（纯缓存） |
| 索引重建 | 117 s | 每次增量后付一次 |
| 摄取 | 单进程 20 min/1,103 份 | 全量 10.8 万份 ≈ 33 h |

**当前方案本机上限**：内存预算 3GB ÷ 3KB/chunk ≈ **100 万 chunk ≈
2,000–3,000 份 PDF**。超过即内存交换、整机卡死。

## 2. 目标规模（近 5 年全 A 股）

- PDF：5,400 家 × 4 份/年 × 5 年 ≈ **10.8 万份**（~110GB 原件）
- chunk：每家每年 ~1,100 块 → **3,000 万块**（区间 2,000–6,000 万）
- 文本层：3,000 万 × 280B ≈ **8.5 GB**
- FTS5 索引：文本的 1–2.5× ≈ **10–20 GB**
- **本机磁盘合计 ~25GB < 47GB 可用** ✅（原始 PDF 不入库）

## 3. 架构决策

### 3.1 检索层：SQLite FTS5（磁盘倒排）取代内存 postings

- `fts5` 虚拟表两列：`content_w`（摄取时 jieba 预分词、空格分隔）+
  `content_c`（trigram，截前 N 字）——双路语义平移，`bm25()` 打分同族
- 查询走 SQL：内存与容量**解耦**，RAM 常驻降到页缓存 ~2GB
- 段式增量合并：**加块即插，无全量重建**（117s 税作废；pickle 缓存层删除）
- 公司/期间过滤 = `WHERE doc_id IN (...)` 连接，替代 numpy 布尔掩码
- 保留 `Corpus.search()` 签名：graph 层零改动（接口不变的兑现时刻）

**为什么不是 ES**：单机单用户下 JVM 集群是负资产；ES 平移条件
（多查询方/跨机）写进 README 升级路径。

### 3.2 存储 schema 归一

```
chunks(rowid INTEGER PRIMARY KEY, doc_id INT FK, page INT, seq INT,
       text TEXT, is_table INT, num_notes TEXT)
-- chunk_id 全字符串主键（17字符×60万行≈17MB）→ 运行时拼接
-- docs 表整型主键 + manifest 照旧（增量账本设计已正确）
```

分年分库（2022.db…2026.db）：备份粒度、ATTACH 跨年查询、单库体积可控。

### 3.3 摄取并行化

PDF 抽取 CPU-bound → `multiprocessing.Pool(8)`；全量 33h → **~5h**（一次性）。
进程内 jieba 各自初始化；失败文件逐个跳过不阻塞（现有容错照旧）。

### 3.4 不变的（架构红利兑现）

manifest 指纹增量 / 孤儿清理 / 幂等跳过；LangGraph 纠错环与期间守卫；
抽取式+对账校验；evalx 评估集；heuristic/llm 双模式。

## 4. 容量与性能预算（验收标准）

| 项 | 目标 |
|---|---|
| 全量入库（10.8万 PDF 文本层） | ≤ 6h（8 核） |
| 增量（单份新财报 → 可查） | ≤ 30s |
| 检索延迟 @3,000 万块 | ≤ 100ms（FTS5 + 过滤下推） |
| 内存常驻 | ≤ 2.5GB |
| 磁盘（不含原始 PDF） | ≤ 30GB |
| evalx 回归 | 样例集指标不降（retrieval@3 ≥ 0.875） |

## 5. 迁移步骤（增量、可回滚）

1. FTS5 检索实现 + `Corpus.search` 适配器；现有 60 万块上 A/B 对比延迟与
   排序质量（evalx 当裁判），通过后切换默认
2. schema 归一 + 分年分库迁移脚本（旧库只读保留至验证完成）
3. 摄取并行化
4. 删 pickle 缓存层（-497MB）与 git 孤立对象（-129MB）
5. GitHub Actions CI（pytest + evalx 样例集）+ README 工程化（徽章/边界声明）

## 6. 诚实边界（开源 README 同步声明）

- 单机单用户设计（sqlite 哲学）；并发查询方 >1 → 检索层平移 ES
- 原始 PDF 不入库：外接 SSD 或巨潮按需重拉（cninfo-disclosure）
- 向量第三路：bge + Milvus/pgvector 待「排行榜证明增益 > 运维成本」后启用
- trigram 列若索引膨胀超预算，降级为纯词法列（中文 jieba 已覆盖主路径）
